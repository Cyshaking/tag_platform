## 【Slide 3 · 业务场景与痛点】⏱ 约 45s

**（先指左边深蓝色项目背景卡）**

> 先看项目本身。我们要做的是保险行业的标签配置平台：从数据源接入、元数据建模、业务主题抽象，到标签任务配置、三级审批、自动生成 SQL 并执行。技术栈 FastAPI + SQLAlchemy + SQLite + 原生前端。

**（再指右边五个痛点，挨个点）**

> 传统做法的问题，我归纳成**五个痛点**：
> 
> ① **需求模糊**。业务同学给的是零散的 SQL 模板片段——"CASE WHEN A 表等于 x，或者 B 表等于 y"——没有完整规范，边界条件反复变。
> 
> ② **复杂 SQL 生成**。CASE WHEN 多表 AND/OR 条件链，还要 BFS 求表关联路径，手写很容易错，改一处漏一处。
> 
> ③ **文档维护负担**。我们约定需求变更必须同步改三份 Word 文档——PRD、方案设计、测试报告——手动改特别容易漏。
> 
> ④ **测试对齐成本**。业务规则一变，已有测试大面积失败，手动对齐耗时，甚至有人会忍不住直接把失败用例删掉，让结果好看点。
> 
> ⑤ **硬编码绝对路径**。数据库里 datasource 表把 config.yaml 里的相对路径解析成了机器专属的绝对路径。别人 clone 源码下来，启动后数据源直接用不了。

## 【Slide 4 · 提示工程 + Agent 八步闭环】⏱ 约 60s 🌟重点讲

**（先指顶部八步流程图，从左到右一遍划过）**

> 面对这五个痛点，我和 Agent 之间形成了一套固定的工作流。总共八步——
> 
> 人类先**输入需求**，Agent 先**收敛成结构化确认稿**——**不动代码不动文档**，只输出 SQL 模板、UI 区块、入参 schema 这些可确认的东西；然后**人类决策敲板**，比如"算子从 6 个加到 13 个""配置表可以选主题表自己"；确认后 Agent 才开始 **先改文档、再改代码、再修测试**，最后做**全量回归和 Git 提交**。

**（再指底部五条圆形标记的提示策略）**

> 这个流程里，**五条提示工程策略**是最关键的：
> 
> **① 文档先行**。不管 Agent 多强，需求边界没锁定就让它写代码，一定会写偏。先改 PRD 和设计文档，人类确认完再动代码，返工成本至少省 70%。
> 
> **② 明确验证标准**。每次给 Agent 任务，我都会附带具体的 pytest 命令和期望结果，比如"必须 154 passed / 0 failed"。有了可度量的标准，Agent 会自己跑、自己修，直到达标才报告。
> 
> **③ 预定义硬约束**。项目一开始就立了几条铁律：不得改既有接口、不得伪造测试、一次只改一个主题。Agent 记住后每个版本都会主动遵守。
> 
> **④ 模糊需求 → 确认稿**。人类说的经常是"加且或关系"这种模糊描述，Agent 要先输出一份完整方案——SQL 模板、UI 区块、入参 JSON，把不确定的列出来等人类拍板，而不是直接动手。
> 
> **⑤ 会话接力机制**。TRAE 每个会话独立，切换前 Agent 会自动生成项目状态汇总——技术栈、已完成功能、当前版本、踩过的坑——我复制到新会话开头，新 Agent 立刻能接上。

## 【Slide 5 · 案例一 SQL + 案例二 测试对齐】⏱ 约 65s 🌟重点讲

### 案例一：SQL 双层结构（35s）

**（先指顶部红色"❌问题"卡）**

> 第一个最头疼的困难——**字段配置模式**。人类给的输入只有：
> "前端可以选表和字段判断逻辑，加且或关系，最终 SQL 要长成 CASE WHEN A.col = x OR B.col = y THEN xxx END。"
> 就这样。没有说主题表怎么处理，没有说多表怎么 JOIN，全是模糊的。

**（指中间蓝色"Agent 收敛方案"卡）**

> Agent 的做法让我印象很深——**它没有直接写代码**，而是把模糊描述收敛成了一套固定规则：
> 外层 = 主题表 LEFT JOIN；
> 内层 FROM = 用户选的第一张配置表；
> 内层 JOIN = BFS 求所有配置表间路径，全部 INNER JOIN；
> 还要反推出配置表到主题表的 FK 字段；
> 最后统一 13 种算子渲染。
> 整套规则，Agent 一次性想清楚，输出成确认稿让我拍板。

**（指右边绿色"✅结果"卡）**

> 确认后 Agent 重写了 sql_generator.py。一开始 17 个测试失败——入参结构变了。Agent 逐个修逐个跑，最后全绿，真实 SQL 输出跟业务模板几乎一模一样。

### 案例二：测试对齐（30s）

**（指底部"修复前"红条和"Agent 修复后"绿条）**

> 第二个案例是**行为变更后的测试对齐**。V1.5 业务决策：元数据接入不需要审批了。pytest 报告 12 个失败：1 个断言 status 还是 pending，另外 11 个用 META_DATA 类型提交审批——现在被拒了。
> 
> 传统做法可能直接删 12 个用例。Agent 没有，它做了四件事：
> 第一，断言从 pending 改成 approved；
> 第二，11 个 META_DATA 测试改成 TAG_TASK 类型；
> 第三，新建 sample_tag_task fixture；
> 第四，**新增了 6 个 V1.5 专属用例**——metadata 提交审批会被拒、删除已结束工单成功、删除审批中的工单会被阻断。

**（指底部绿色大横幅）**

> 结果就是——**160 passed / 0 failed，还多了 6 个用例**。

## 【Slide 6 · 案例三 数据源相对路径】⏱ 约 30s 🌟今天刚完成

**（指顶部问题卡片 + 假 DB 记录块）**

> 第三个案例是**今天刚修完的**——数据源硬编码绝对路径。
> 
> 根因是 config.yaml 里写的是 `./data/insurance_demo.db`，但种子函数用 config.py 里的方法把它解析成了**机器专属的绝对路径**——比如我这台电脑就是 `D:\Trae\tag_platform\data\insurance_demo.db`，存进了 datasource 表。
> 
> 别人 clone 源码下来，启动后点"执行 SQL"直接报错——那个路径根本不存在。

**（指中间三个圆形编号的修复项）**

> 怎么修的？三处改动，不碰任何既有接口：
> 
> 第一，`config.py` 新增 `sqlite_path_raw()` 返回 config.yaml 里的原始相对路径——跟原来返回绝对路径的方法分离；
> 第二，种子函数改用 `sqlite_path_raw()` 写 datasource，新种子存相对路径；
> 第三，`sqlite_engine.py` 新增 `_resolve_db_path()` 函数——相对路径自动拼项目根解析成绝对路径，绝对路径原样返回，这样老数据也不受影响。

**（指底部蓝底 Before/After）**

> 改完后，数据库那条记录从 `D:\Trae\...` 变成了 `./data/insurance_demo.db`。两轮 pytest 全量回归 160 过，引擎直接传相对路径执行 SQL 也验证通过。现在别人 clone 下来直接 `python run.py` 就能用。

## 【Slide 8 · 总结 · 价值 · 致谢】⏱ 约 30s

### AI 提效对比（15s）

**（指顶部对比表格，从上到下快速扫）**

> 最后对比一下传统开发和 AI 辅助。六个维度：
> 
> 需求收敛省 70%，文档编写省 80%，代码实现省 50%，测试修复省 60%，文档同步从经常忘变成每次必做，质量保障从可能删用例变成改断言+新增用例——我们的 160 个用例里有 6 个是修复过程中新增的。

### 三条结论 + 致谢（15s）

**（指中间三个圆形编号）**

> 总结三条：
> 
> 第一，**人类定规则 + Agent 跑流程**是可行的分工模式。
> 
> 第二，**文档先行是最关键的策略**。需求边界锁定了代码就不会写偏。
> 
> 第三，**AI 辅助不等于无约束**。人类必须亲自跑 pytest 做最终验证。

**（指右边局限性清单 + 右下角 THANK YOU，微笑）**

> 当然也有局限——Agent 需要人类定边界、业务决策不能代劳、外部环境需人工介入。
> 
> 我的汇报就到这里，欢迎大家提问。谢谢！
