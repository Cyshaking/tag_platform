# AI 辅助开发实践总结报告

> —— 标签配置管理平台（tag_platform）V1.0 → V1.6 + 补丁 全过程复盘
> 
> 项目仓库：https://github.com/Cyshaking/tag_platform

---

## 一、项目概况

**标签配置管理平台**是一个面向保险业务场景的全栈 Web 应用，覆盖从数据源接入 → 元数据建模 → 业务主题抽象 → 标签任务配置 → 三级审批 → SQL 生成与执行的完整链路。

| 维度 | 内容 |
|------|------|
| 技术栈 | FastAPI + SQLAlchemy 2.x + SQLite + pytest + 原生 HTML/JS 前端 |
| 代码规模 | 后端 ~30 Python 文件（models / routers / services / schemas / engines / utils），前端 ~10 静态页面 |
| 数据库 | 14 张业务表，7 个模块使用统一 serial_no 编号体系 |
| 测试覆盖 | pytest unit / integration / engines 三层，最终 **160 passed / 0 failed** |
| 版本跨度 | V1.0 → V1.1（字段配置模式）→ V1.2（三级审批）→ V1.3（权限）→ V1.4（UI）→ V1.4.3（编号）→ V1.5（免审批+删除）→ V1.6（日志）+ **数据源硬编码路径补丁** |

本项目**全程由 1 名开发者 + TRAE AI Agent 协作完成**，从需求收敛、文档编写、代码实现、测试到部署推送，AI 参与了几乎每一个环节。

## 二、使用的 AI 工具

### 2.1 TRAE IDE + Agent 能力

核心工具是 **TRAE**——一款内置 AI Agent 能力的编程 IDE。Agent 在项目中实际用到的能力：

| Agent 能力 | 在本项目中的典型用途 |
|------------|----------------------|
| 代码搜索与理解 | 跨 30+ 文件理解 SQL 生成逻辑、BFS 路径求解、审批状态机 |
| 代码编写与重构 | 重写 `sql_generator.py`、新增/修改 router/service/schemas |
| 文档编写 | 用 python-docx 编辑三份 Word 文档（PRD / 方案设计 / 测试报告） |
| 测试生成与修复 | V1.5 行为变更 12 失败，自动定位 + 修改断言 + 新增 6 个专属用例 |
| Shell 命令执行 | 启停服务、跑 pytest、git 提交、查端口、排查网络问题 |
| 浏览器预览 | 打开本地服务验证 UI 渲染效果 |
| Git 工作流 | 分组提交、推送远程、处理网络超时 |

### 2.2 辅助工具

- **python-docx**：Agent 用 Python 脚本直接编辑 `.docx` 文件（也踩到了样式 ID 的坑）
- **pytest**：Agent 通过 Shell 执行 pytest，根据输出自动定位并修复
- **Git**：Agent 执行 `git add/commit/push`，遇到 GitHub 网络阻断时帮着诊断 DNS/Ping/TCP

## 三、任务分工方式

### 3.1 人类开发者负责

| 职责 | 具体内容 |
|------|----------|
| **需求输入** | 业务背景、SQL 模板、UI 原型方向（如"CASE WHEN tableA.col = 'xxx' OR tableB.col = 'xxx'"） |
| **关键决策** | 算子列表是否够用、配置表选择范围、审批流程是否变更等业务决策 |
| **边界约束** | 明确"文档先行""一次只改一个主题""不改变现有功能语义""不伪造测试结果"等铁律 |
| **最终验证** | Agent 给出改动后，人类在真实场景下验证（登录、新建任务、跑审批流） |
| **资源协调** | 关闭被锁的 Word 文档、切换网络、在 Agent 卡住时提供新思路 |

### 3.2 AI Agent 负责

| 职责 | 具体内容 |
|------|----------|
| **需求收敛与结构化** | 把模糊需求转化为确认稿（固定 SQL 结构、明确 UI 区块、JSON 入参 schema） |
| **代码实现** | 按确认稿一次性修改所有受影响文件（文档 → 后端 → 前端 → 测试） |
| **测试修复** | 根据 pytest 失败输出自动定位根因，修改断言或重写用例 |
| **文档同步** | 代码变更后自动将三份 Word 文档对齐到最新版本 |
| **Git 操作** | 分组提交、推送远程、处理简单冲突 |
| **问题排查** | 网络诊断、SQL 输出不符合预期时检查中间步骤 |

### 3.3 不可越过的红线

1. **不得伪造测试结果**：Agent 必须如实报告 pytest 结果，不能通过删除测试用例让结果变好看
2. **不得擅自启动/占用端口**：人类未明确要求前，Agent 不得运行 `python run.py`
3. **不得跨主题混改**：一次只处理一个版本主题
4. **不得以重构为由改动可用代码**：没有明确任务依据时不动已通过测试的代码

## 四、关键提示工程策略

### 4.1 文档先行——约束执行顺序

每次需求变更时给 Agent 的指令固定为：

> **"先改 PRD + 方案设计文档 → 再改后端代码 → 再改前端 → 最后跑全量测试"**

好处：锁定需求边界，代码不会写偏；避免返工（如果直接写代码后发现需求理解有误，回退成本远高于先改文档）。

### 4.2 明确验证命令

每次任务附带可度量的验证标准，例如：
> "完成后执行 `python -m pytest tests/ -q`，必须 **160 passed / 0 failed**"

Agent 有了明确的成功标准，会主动跑、自己修、直到达标。

### 4.3 约束规则前置

项目初期就给 Agent 设定一组**永不修改的硬约束**（不得改既有接口、不得伪造测试、一次一主题等），Agent 记住后每个版本都会主动遵守。

### 4.4 模糊需求 → 结构化确认稿

Agent 先**不动代码不动文档**，只输出结构化确认稿（SQL 模板 + UI 区块表 + 入参 JSON + 待决策问题清单），等人类拍板后再执行。

### 4.5 会话接力机制

TRAE 每个会话独立，切换前 Agent 自动生成项目状态汇总（技术栈、已完成功能、当前版本、踩过的坑），人类复制到新会话开头即可，省去从零讲背景的成本。

## 五、Agent 工作流程

稳定的**八步闭环**：

```
需求输入 → 需求收敛确认稿 → 人类决策敲板 → 文档修改 → 代码实现 → 测试修复 → 全量回归 → 文档同步 + Git 提交
```

两个关键反馈回路：
- **文档 → 人类 → 代码**：文档改完人类可发现理解有误，退回重写，不等代码写完才发现
- **测试 → 代码 → 测试**：pytest 失败时 Agent 自己修，直到全绿，人类无需介入

## 六、遇到的问题及改进措施

### 6.1 Word 文档锁文件

**问题**：python-docx 写 `.docx` 时被 WPS 占用会失败。
**改进**：Agent 先 `tasklist | findstr wps` 查进程，提示人类关闭，后续主动检查锁文件。

### 6.2 python-docx 样式 ID

**问题**：`style_id` 必须用无空格的 `Heading1`，不能用带空格的 `Heading 1`，否则回退为 Normal。
**改进**：确认正确映射表后统一使用，未再出错。

### 6.3 GitHub 网络阻断

**问题**：WLAN 屏蔽 TCP 443，推送失败。
**改进**：Agent 执行完整连通性诊断（DNS → Ping → TCP），精确定位后建议切换网络，同时把本地 commit 状态清晰报告给人类。

### 6.4 测试对齐（V1.5）

**问题**：元数据免审批 → 12 个已有测试失败（1 个断言 pending、11 个 META_DATA 类型）。
**改进**：Agent 没有删用例，而是改断言 + 重写 fixture + 新增 6 个 V1.5 专属用例。最终 **160 passed / 0 failed，还多了 6 个用例**。

### 6.5 会话隔离

**问题**：TRAE 会话独立，新会话 Agent 对项目一无所知。
**改进**：每次切换前 Agent 生成项目状态汇总，形成约定俗成的"会话接力"机制。

### 6.6 Uvicorn reload=False

**问题**：`run.py` 的 uvicorn 启动参数 `reload=False`，改完代码热更新不生效。
**改进**：Agent 在 README 和会话汇总中记录此点，后续改完代码主动"停进程 → 重新启动"。

### 6.7 数据源硬编码绝对路径（补丁 · 2026-11-09）

**问题**：数据库 datasource 表中，种子函数 DAT20261105003 的 `config_json.db_path` 被写成机器专属绝对路径（如 `D:\Trae\tag_platform\data\insurance_demo.db`）。别人 clone 源码后数据源执行 SQL 直接失败。

**根因**：`config.py` 的 `sqlite_path()` 把 config.yaml 里的相对路径 `./data/insurance_demo.db` 解析成了绝对路径返回。种子函数内部创建文件确实需要绝对路径（mkdir + CREATE TABLE），但不该存进 datasource 表。

**排查**：人类在数据源管理页面发现绝对路径 → 追溯 `seed_data.py` 的 `_demo_db_path()` → 定位到 `config.py` 的 `sqlite_path()`。

**修复（三处改动，不碰既有接口）**：

| 文件 | 改动 |
|------|------|
| `config.py` | 新增 `sqlite_path_raw()` 返回 config.yaml 原始相对路径；原 `sqlite_path()` 保持不变（种子内部仍需绝对路径） |
| `seed_data.py` | datasource 的 `config_json` 改用 `sqlite_path_raw()` |
| `sqlite_engine.py` | 新增 `_resolve_db_path(db_path)`：相对路径拼 `BASE_DIR` 解析为绝对路径；绝对路径原样返回（兼容历史数据） |

同时 UPDATE 数据库 DAT20261105003，把现有记录的 config_json 改为 `{"db_path": "./data/insurance_demo.db"}`。

**验证**：两轮 pytest 全量回归均 **160 passed / 0 failed**；直接传相对路径执行 `SELECT COUNT(*) FROM policy` 成功；历史绝对路径数据也不受影响。

## 七、AI 辅助开发的实际价值

### 7.1 效率提升

| 维度 | 传统开发 | AI 辅助 |
|------|----------|--------|
| 需求收敛 | 自己写模板/画原型 | Agent 输出结构化确认稿（省 70%） |
| 文档编写 | 手动开 Word 逐章改 | python-docx 脚本一次性改（省 80%） |
| 代码实现 | 逐文件写易漏改 | 一次性改完所有受影响文件（省 50%） |
| 测试修复 | 手动定位写用例 | pytest 失败自动修复+新增用例（省 60%） |
| 文档同步 | 经常忘记更新 | 每次版本最后强制执行（从遗漏 → 必完成） |

### 7.2 质量保障

- **测试不打折扣**：V1.5 行为变更 12 失败，Agent 改断言 + 重写 fixture + 新增 6 个专属用例，传统开发中很容易被"暂时跳过"
- **文档与代码同步**：Agent 把"文档同步"作为每次版本的最后一步，形成硬性习惯
- **自动化验证闭环**：改完代码自动跑 pytest、失败自动修直到全绿，人类无需介入
- **路径可移植**：数据源补丁体现"分层处理"——种子内部用绝对路径 + datasource 存相对路径 + 引擎运行时解析，历史数据不受影响

### 7.3 复杂逻辑处理

V1.1 的 SQL 生成逻辑：外层主题表 LEFT JOIN + 内层 FROM 第一张配置表 + 内层 JOIN BFS 求路径 + FK 反推 + AND/OR 条件链 + 13 算子。人类自己实现需反复调试 BFS 路径、反推 FK、条件链前缀等边界，Agent 一次性实现 + 修 17 个测试失败通过。

## 八、AI 辅助开发的局限性

### 8.1 需要人类定义边界和约束

Agent 无法自己判断"改动是否会影响既有行为"。如果人类没设"不改变既有功能语义"，Agent 在 V1.1 重写 sql_generator 时可能顺手改掉 SQL 直配模式的约定，导致大面积回归失败。

### 8.2 业务决策必须人类拍板

算子列表从 6 → 13、配置表选择范围、元数据是否审批——这些是业务决策不是技术决策。Agent 可以给方案但不能替人类拍板。

### 8.3 外部环境问题需人工介入

GitHub 网络阻断、WPS 锁文件、手机热点切换——Agent 可以诊断原因，但解决手段必须人类执行。

### 8.4 会话隔离的传递成本

每个会话独立，切换时手动复制项目汇总。若有持续上下文能力可省略此环节。

### 8.5 对"坏代码"无免疫力

Agent 基于当前代码库实现功能。如果代码库质量不好，Agent 会在糟糕基础上继续堆功能，不会主动重构。

### 8.6 伪造风险需防范

Agent 可以伪造测试结果（删用例、改数量）。人类应对措施：偶尔自己跑 pytest + 最终交付前完整端到端验证。

## 九、总结

### 9.1 核心结论

AI 辅助开发证明了**"人类定规则 + Agent 跑流程"**模式可行且高效：

- 人类负责：需求方向、业务决策、约束设定、最终验证
- Agent 负责：模糊需求结构化、代码实现、测试修复闭环、文档同步、Git 操作

### 9.2 可复制的实践清单

| # | 实践 | 重要性 |
|---|------|--------|
| 1 | 文档先行（PRD → 方案 → 代码 → 测试） | ⭐⭐⭐⭐⭐ |
| 2 | 明确验证标准（具体 pytest 命令 + 期望结果） | ⭐⭐⭐⭐⭐ |
| 3 | 预定义硬约束（不得改既有接口、不得伪造测试等） | ⭐⭐⭐⭐⭐ |
| 4 | 模糊需求 → 确认稿再执行 | ⭐⭐⭐⭐ |
| 5 | 会话接力机制（Agent 生成项目状态汇总） | ⭐⭐⭐⭐ |
| 6 | 人类亲自做最终端到端验证 | ⭐⭐⭐⭐ |
| 7 | 路径问题分层处理（种子内部绝对 + datasource 存相对 + 引擎运行时解析） | ⭐⭐⭐ |
| 8 | 每次版本最后同步更新三份文档 | ⭐⭐ |

### 9.3 未来可改进方向

- **持续上下文能力**：让 Agent 在多会话间自动保持项目状态
- **约束自动检查**：Agent 代码实现后自动 diff 检查是否触碰既有接口/状态流转
- **环境恢复自动化**：网络恢复后自动重试推送、服务重启后自动跑冒烟测试
- **可移植性巡检**：Agent 自动扫描硬编码绝对路径并提示修复
